# Findings — deduplicate the redundant build in `dogfood-test.sh`

## TL;DR

`scripts/dogfood-test.sh` runs `pnpm run --silent build` before
`node dist/scripts/dogfood-smoke.js`. `goals/_meta.gates.sh` M.4
already builds every app. When `completion-check.sh` runs them in
parallel, both invoke `tsc` writing into the same `dist/` tree — race
condition. Observed empirically 2026-05-23: parallel completion-check
randomly fails on goal-0 0.3 "Self-dogfooding"; serial run (and
standalone) passes.

The clean fix is **deduplicate the action**: `dogfood-test.sh`
consumes the `dist/` produced by M.4 instead of producing its own. If
`dist/scripts/dogfood-smoke.js` is missing, fail with a clear "run
pnpm build first (or rely on `_meta` M.4)" message rather than
silently rebuilding.

## Why this is the right fix (vs alternatives)

Per the in-tree isolation findings, three patterns address parallel
resource contention:

| Pattern                | When                                                         | This case                                                                                |
| ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| **Deduplicate**        | Same expensive action invoked from multiple places           | `pnpm build` is invoked from both M.4 and 0.3 — text-book dedup case                     |
| **Isolate per-worker** | Mutable state that can be cheaply namespaced (DB, port, log) | Build outputs are large + path-dependent (Node module resolution) → expensive to isolate |
| **Lock**               | Single shared external resource (Docker daemon, GitHub API)  | N/A — no such resource here                                                              |

Dedup wins because the build is **expensive** and **path-coupled**.
Isolating would require two separate output dirs and rewriting Node
module resolution per worker. Locking would serialize two builds that
should never have been duplicated in the first place.

## The concrete change

Edit `scripts/dogfood-test.sh`:

```bash
#!/usr/bin/env bash
# dogfood-test.sh — API-level self-test for the in-memory MVP.
#
# Consumes the build produced by goals/_meta.gates.sh M.4. Does not
# rebuild — that would race with M.4 on dist/.

set -euo pipefail

ROOT="$(cd "$(dirname "$0")/.." && pwd)"
cd "$ROOT"

LOG="$ROOT/.state/dogfood.log"
mkdir -p "$(dirname "$LOG")"
: > "$LOG"

note() { echo "[dogfood] $*" | tee -a "$LOG"; }

SMOKE_JS="$ROOT/dist/scripts/dogfood-smoke.js"
if [ ! -f "$SMOKE_JS" ]; then
  note "✗ $SMOKE_JS missing"
  note "  Build first: pnpm run build  (or run goals/_meta.gates.sh M.4)"
  exit 1
fi

note "Run in-memory dogfood smoke"
node "$SMOKE_JS" >>"$LOG" 2>&1
note "✓ dogfood test passed"
```

## Side effect: standalone execution

Running `bash scripts/dogfood-test.sh` directly without a prior build
will now fail with the explicit message instead of silently
rebuilding. This is intentional: the contract becomes "dist/ must
exist," which is a stronger and clearer dependency. CI and the chain
both run M.4 before 0.3 (after this fix lands), so the dependency is
satisfied in normal flows.

If someone wants the old behavior, they explicitly invoke
`pnpm run build && bash scripts/dogfood-test.sh`. The orchestrator
doesn't need to.

## Verification

After the fix, run:

```
VSPEC_GATES_NO_CACHE=1 bash scripts/completion-check.sh
```

twice in a row. Both should hit `ALL_DONE` with no goal-0 0.3 flake.
Without the fix, the same two runs randomly produce goal-0 0.3
failures (observed 2026-05-23).

## Why P0

Goal-30 (now also a P0 findings doc) execution requires reliable
chain runs. Every TDD iteration touches the chain via
`active-check.sh` or `completion-check.sh`. A flaky chain conflates
real test failures with infrastructure flakes — agents waste time
debugging the wrong thing.

The fix is one file edit. The cost of _not_ fixing is paid every
parallel chain run during goal-30 implementation.

## Reference: the same pattern elsewhere

Watch for any other gate or script that invokes `pnpm build`,
`pnpm install`, or similar expensive shared-output actions. The
honest list is "M.4 owns `dist/`; everything else consumes." Anything
that doesn't follow this is a candidate for the same dedup treatment.
The in-tree-isolation findings doc tracks the broader sweep.

## Resolution

Closed by `7cc4396` (`fix(harness): stop dogfood script from rebuilding`).
`scripts/dogfood-test.sh` now consumes `dist/scripts/dogfood-smoke.js`
without invoking `pnpm build`, and
`apps/api/tests/integration/dogfood-test.test.ts` proves the script does
not call `pnpm` before running the smoke.
